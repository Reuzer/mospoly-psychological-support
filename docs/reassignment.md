# Переназначение заявок и встреч на текущего психолога

Психолог может взять на себя заявку, которая ожидает подтверждения пользователя,
или уже созданную встречу со статусом `awaiting`. Назначаемый специалист определяется
по текущему авторизованному пользователю и его профилю психолога.

Оба запроса требуют cookie `access_token`, роли `psychologist` и существующего
профиля `Psychologist`, связанного с текущим пользователем. Поля назначения
не передаются клиентом: `psychologist_id` записывается как ID профиля психолога,
а `assigned_to` связанной заявки — как ID пользователя этого психолога.

## Заявка, ожидающая подтверждения

```http
POST /applications/{application_id}/reassign
Content-Type: application/json
Cookie: access_token=<token>
```

Операция доступна для заявки со статусом `awaiting_user_confirmation`.
Тело JSON обязательно. Пустой объект `{}` меняет только назначенного психолога,
сохраняя текущие условия предложения. Для изменения условий можно передать поля:

| Поле | Тип | Значение |
| --- | --- | --- |
| `meeting_type` | `"offline"` или `"online"` | Формат консультации; явный `null` запрещен |
| `scheduled_at` | Строка datetime | Дата и время; явный `null` запрещен; рекомендуется явный часовой пояс |
| `location_address` | Строка или `null` | Адрес для очной консультации; максимум 128 символов; строка должна содержать непробельные символы |
| `meeting_url` | Строка или `null` | Ссылка для онлайн-консультации; максимум 128 символов; строка должна содержать непробельные символы |

Пропущенные поля берутся из текущего предложения, включая адрес и ссылку.
При смене формата очищается неактуальное поле: у `online` — адрес, у `offline` —
ссылка. Перед записью проверяются итоговые условия: формат и время должны быть
определены, для `offline` нужен адрес, для `online` — ссылка. Поэтому при смене
формата необходимо обеспечить условие нового формата, если его еще нет в
сохраненных данных. Время должно быть в будущем; учитываются периоды
недоступности нового психолога.

Все неизвестные поля запрещены. Попытка передать `psychologist_id`,
`assigned_to`, `patient_id` или другой дополнительный ключ возвращает `422`.
Пустая или состоящая из пробелов строка адреса/ссылки, а также `null` в
`meeting_type`/`scheduled_at` тоже дают `422`. Если после объединения данных
нужный для формата адрес или ссылка равен `null`, возвращается `400`.

Пример смены формата консультации:

```json
{
  "meeting_type": "online",
  "scheduled_at": "2026-11-10T15:00:00+03:00",
  "meeting_url": "https://example.com/consultation"
}
```

При успехе заявка назначается текущему психологу, `assigned_to` становится
ID его пользователя, `confirmation_requested_at` обновляется, а `version`
увеличивается. Статус остается `awaiting_user_confirmation`: пользователь
подтверждает предложение после смены специалиста и условий обычным запросом
`POST /applications/{application_id}/confirm`.

Ответ `200 OK` — полная заявка в формате `ApplicationResponse`, включая
вложенные `psychologist`, `assigned_to_user`, обновленные условия, статус,
`confirmation_requested_at` и `version`.

## Уже созданная встреча

```http
POST /appointments/{id}/reassign
Cookie: access_token=<token>
```

Тело запроса отсутствует. Операция доступна для встречи со статусом `awaiting`,
дата и время которой строго позже текущего момента. Психолог с собственным
профилем может взять на себя встречу другого психолога.

Проверка времени выполняется после блокировки записи и повторяется перед
изменением данных после ожидания остальных блокировок. Время сравнивается
в UTC; время без часового пояса трактуется как UTC. Если встреча уже началась
или её время наступило точно в текущий момент, сервер возвращает `409`:

```json
{"detail": "Нельзя переназначить запись, время которой уже наступило"}
```

При отказе запись, связанная заявка и запросы переноса остаются без изменений.

Переназначение происходит сразу. Встреча получает профиль текущего психолога,
обновляется `last_change_time`; `scheduled_time`, `remind_time`, `venue`,
`type`, `comment` и статус `awaiting` сохраняются. Пользователю не требуется
повторно подтверждать встречу.

Если встреча связана с заявкой, назначенный психолог и `assigned_to` заявки
обновляются в той же операции. Связь учитывается по `Appointment.application_id`
и `Application.appointment_id`. У связанной заявки обновляется `updated_at`,
увеличивается `version`; ее условия и статус сохраняются.

Ожидающие решения запросы переноса этой встречи получают статус `rejected`,
`responded_at` и причину `Запись переназначена другому психологу`:
они больше не могут изменить встречу после смены специалиста. История
обработанных запросов переноса сохраняется; встреча не отменяется.

Если текущий психолог уже назначен на встречу, запрос возвращает `200` с
текущей встречей без повторного изменения времени, связанных заявок и запросов
переноса. Для этого также требуется будущее время встречи. Завершенная,
отмененная встреча или встреча с уже наступившим временем возвращает `409`,
в том числе при повторном запросе текущего психолога.

Ответ `200 OK` — встреча в формате `AppointmentBase`, включая вложенные
`patient`, нового `psychologist`, `application_id`, условия встречи и
обновленный `last_change_time`.

## Ошибки

| HTTP | Заявка | Встреча |
| --- | --- | --- |
| `200` | Заявка переназначена и ожидает подтверждения | Встреча переназначена сразу либо уже принадлежит текущему психологу |
| `400` | Недопустимы итоговые условия или новый психолог недоступен | Не используется |
| `401` | Нет действительной авторизации через `access_token` | То же |
| `403` | Нет роли психолога или собственного профиля | То же |
| `404` | Заявка не найдена | Встреча не найдена |
| `409` | Статус отличается от `awaiting_user_confirmation` или конфликт версии | Статус отличается от `awaiting`, время встречи уже наступило, психолог недоступен или конфликт состояния |
| `422` | Некорректный UUID, отсутствующее/неверное JSON-тело, тип поля, дата, enum, запрещенный `null`, пустая строка или дополнительное поле | Некорректный UUID |

Доменные ошибки возвращаются в форме `{"detail": "Описание ошибки"}`.
Ошибки валидации FastAPI (`422`) содержат массив `detail` с указанием полей.

В интерфейсе после `200` следует обновить данные из ответа: для заявки
показывать ожидание подтверждения нового предложения, для встречи — сразу
нового психолога. После `409` следует перечитать актуальное состояние сущности.

## Подтверждение изменённых условий

`POST /applications/{application_id}/confirm` требует JSON с версией предложения,
полученной пользователем при последнем чтении заявки:

```json
{"expected_version": 4}
```

Только владелец заявки может подтвердить её. Психолог, время, формат и место
создаваемой записи берутся из сохранённой заявки. `appointment_id` и другие
дополнительные поля в теле запрещены. Если после чтения заявки психолог изменил
условия, сервер возвращает `409`; клиент должен получить и показать новые условия
и отправить их версию только после нового согласия пользователя.

Подтверждение и создание записи выполняются в одной транзакции с блокировкой
заявки. Параллельные и повторные подтверждения не создают дубликаты. Прямое
создание записи через `/appointments/create` с непустым `application_id`
возвращает `400`, чтобы исключить обход подтверждения условий заявки.

Длина адреса и ссылки при переназначении ограничена 128 символами — размером
поля `Appointment.venue`. Проверка выполняется и для сохранённых условий:
заявка с более длинным адресом/ссылкой должна быть исправлена перед подтверждением.

## Swagger / OpenAPI

Интерактивная документация доступна по `/docs`, фактическая схема —
по `/openapi.json`. Контроллеры описывают предусмотренные ими ответы:
`400`, `401`, `403`, `404`, `409`, `422`, `429` и `500` там, где они используются.
Для бизнес-ошибок описан строковый `detail`, для ошибок проверки запросов —
массив `detail`; для ограничения частоты запросов — поле `error`.
Регистрация документирована с `201`, пустые успешные ответы не описываются
как JSON, для изображений указан двоичный ответ. Авторизация переназначения
описана через cookie `access_token`.

Файл `swagger.yaml` экспортируется из приложения в JSON-совместимом формате
YAML, чтобы статическая спецификация совпадала с `/openapi.json`:

```bash
python scripts/export_openapi.py
```

После изменения API нужно повторить экспорт. Тест `test_openapi_contract.py`
проверяет совпадение файла с приложением и соответствие HTTP-ошибок схеме.

Проверки PostgreSQL запускаются отдельно с URL тестовой базы:

```bash
PSYCHOHELP_TEST_DATABASE_URL=postgresql+asyncpg://user:password@localhost/test_db \
  python -m pytest tests/test_reassignment_database.py
```

Каждый тест создаёт отдельную случайную схему и удаляет её при завершении;
обычные схемы базы не изменяются. Без указанного URL эти тесты пропускаются.


## Результат повторной проверки требований

| Требование | Итоговая проверка |
| --- | --- |
| Любой психолог берёт заявку на себя | Роль `psychologist`, существующий профиль, назначение по авторизованному пользователю |
| Редактирование на этапе подтверждения | Только `awaiting_user_confirmation`; частичное обновление условий, новая версия и время запроса подтверждения |
| Повторное согласие пользователя | Подтверждает владелец с `expected_version`; устаревшая версия даёт `409` |
| Переназначение существующей записи | Только `awaiting` и строго будущее время; запрещены прошедшие, начавшиеся, завершённые и отменённые встречи |
| Согласованность данных | Назначение связанной заявки обновляется в одной транзакции; ожидающие запросы переноса отклоняются |
| Защита от параллельных операций | Блокировки записей и проверка версии; повторное подтверждение не создаёт дубликаты |
| Условия консультации | Проверяются будущая дата, формат, адрес/ссылка, длина до 128 символов и доступность психолога |
| Swagger | Статическая спецификация совпадает с `/openapi.json`; HTTP-ошибки и успешные ответы покрыты проверками |

Первоначальное предложение через `/applications/{application_id}/offer` теперь
использует ту же проверку итоговых условий, что и переназначение заявки.
Так нельзя обойти проверку обязательного адреса/ссылки, длины места встречи
или недоступности психолога через другой метод API.

При подтверждении заявки время повторно проверяется после блокировок перед
созданием записи. При подтверждении запроса переноса повторно проверяются
будущее время новой встречи, корректность напоминания и доступность
назначенного психолога. Если время устарело или появился больничный/отпуск,
сервер возвращает `400` без изменения записи. Отсутствующий профиль психолога
при запросе переноса возвращает описанный в Swagger `404`.
